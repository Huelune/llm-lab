# 필요한 정의를 LLM이 되묻게 하기 설계

- 작성일: 2026-10-14
- 상태: 구현됨 (2026-10-14)
- 바탕: `2026-10-13-definitions-context-design.md`(참고 정의), `2026-10-14-cross-file-fixes-design.md`(다른 파일 수정),
  `2026-10-14-callers-context-design.md`(호출자). 여기 적지 않은 것은 그대로 따른다.

## 1. 배경과 목표

RTE 작업 2(묶음 80개)에서 직접 수정 41행을 점검 도구로 나눠 본 결과:

- 묶음 80개가 모두 정의 상한(40개)까지 찼다. 이유가 "저장됐지만 요청에 안 붙은 정의"를 짚은 행은 0개라, 상한을 더
  올려도 바뀌지 않는다.
- 18행은 프로젝트 어디에도 선언·구현이 없는 함수 하나를 짚었다(구현이 고른 폴더 밖에 있다).
- 16행은 짚은 이름이 모두 요청에 있었다. 이유를 사람이 읽어 보니 11건이 "RTE 생성 코드나 하위 변환 함수의 구현을
  확인할 수 없다"였다. 붙인 함수가 다시 부르는 함수(한 단계 아래)는 보내지 않기 때문이다.

미리 정해 둔 규칙으로 더 붙이는 방식은 상한이 이미 차 있고, 어느 깊이까지 필요한지 알 수 없다. 그래서 LLM이 판단에
필요한데 보이지 않는 이름을 직접 적게 하고, 서버가 프로젝트에서 찾아 보낸 뒤 다시 판단하게 한다.

목표:
- 필요한 함수 구현이 몇 단계 아래에 있어도 LLM이 받아 보고 판단한다.
- 프로젝트에 없는 이름은 "없음"을 알려 줘서, LLM이 그 함수를 동작을 모르는 외부 코드로 보고 판단하게 한다.
- 첫 요청은 지금과 같다. 되묻기를 끄면(`LLM_FOLLOW_UPS=0`) 보내는 메시지가 지금과 한 글자도 다르지 않다.

### 범위

포함:
- RTE, MISRA C:2012, CodeMetrics 세 종류 모두. 종류마다 되묻기를 쓰는지(`asks_definitions`)를 둔다. 세 종류 모두 켠다.
- 받은 정의를 고칠 수 있는지는 지금의 `edits_definitions`를 따른다: RTE는 고칠 수 있고, MISRA·CodeMetrics는 참고만.
- 되물을 때 찾을 프로젝트 색인, 되묻기로 보낸 정의·파일의 작업 저장, 저장된 답 재사용 규칙, 설정, 점검 도구.

제외:
- tool calling(함수 호출 API). 회사 모델의 지원을 확인하지 않았고, 지금의 JSON 형식 답으로 충분하다.
- 화면(UI) 변경. 대화 기록과 점검 도구로 본다.
- 호출자 되묻기(호출자 조각은 지금처럼 첫 요청에만 붙인다).

## 2. 대화 흐름

묶음 하나를 처리할 때:

1. 첫 요청을 지금처럼 만든다(`make_request`). 되묻기를 켠 종류는 지시문 끝에 되묻기 규칙(3절)이 붙고, 답 형식에
   `need`가 있다.
2. 답을 받는다. 답 형식이 틀리면 지금처럼 한 번 다시 묻는다(이 재시도는 차례마다 한 번).
3. 답의 `need`가 비어 있으면 그 답이 최종이다.
4. `need`가 있고 되물을 차례가 남았으면, 서버가 이름을 프로젝트 색인에서 찾아 다음 사용자 메시지(4절)를 만들어
   대화에 잇고 2로 간다. 이번 답의 판단은 쓰지 않는다(임시).
5. 되물을 차례가 다 찼는데 `need`가 오면, 그 답을 최종으로 쓴다(`need`는 무시).

되물을 수 있는 횟수는 `LLM_FOLLOW_UPS`(기본 2)다. 요청 수는 묶음당 최대 1 + 2 = 3번이고, 형식 재시도를 더하면
최대 6번이다.

## 3. 답 형식과 지시문

답 형식: 되묻기를 켠 종류의 스키마에 최상위 `need`를 더한다. strict 스키마이므로 필수다.

```json
"need": {"type": "array", "items": {"type": "string"}}
```

`LLM_FOLLOW_UPS=0`이면 `need` 없는 지금 스키마와 지금 지시문을 쓴다.

지시문(영어, 종류 공통 문단 하나를 각 종류의 지시문 끝 JSON 안내 앞에 붙인다). `N`은 `LLM_FOLLOW_UPS` 값이다:

> If you need a definition that is not shown to decide (a function body, a macro, a type or a variable), put its exact
> name in "need", at most 10 names. You can ask N times in total. When "need" is not empty your findings are
> provisional: the definitions will be sent and you will answer again. Do not ask for names already shown. Leave
> "need" empty when the code shown is enough.

그리고 각 종류의 지금 문장 "Do not guess definitions (macros, types, other functions) that are not shown. If they
matter, say so in reason."을 되묻기를 켰을 때 다음으로 바꾼다:

> Do not guess definitions that are not shown; ask for them in "need". If a name is not in the project, treat it as
> external code whose behavior is unknown, and say so in reason.

`N`이 지시문에 들어가므로 되묻기 횟수가 다르면 재사용 키도 다르다.

## 4. 되묻기 메시지

`need`의 이름을 이렇게 다룬다:

- C 식별자 모양(`[A-Za-z_][A-Za-z0-9_]*`)이 아닌 것은 버린다. 같은 이름은 한 번만. 앞에서 10개까지.
- 이미 보낸 이름(보낸 코드 범위 안에 정의가 있거나, 이 대화에서 정의를 이미 보낸 이름)은 "이미 위에 있음"으로 알린다.
- 나머지는 프로젝트 색인(5절)에서 찾는다. 이름마다 정의 후보를 지금의 `pick_definitions`와 같은 순서(검사 파일 →
  헤더 → 그 밖)로 2개까지, 별칭 매크로는 가리키는 구현까지(`ALIAS_DEPTH`) 싣는다. 이미 보낸 몸체(파일·시작 줄)는
  다시 싣지 않는다.
- 한 번에 싣는 정의는 20개, 줄 수 합은 600줄까지. 넘치는 이름은 "이번에 다 못 보냄, 필요하면 다시 요청"으로 알린다.

메시지(사용자 역할, 영어):

~~~text
Definitions you asked for. Those marked editable may be changed; set "file" to their path.

```c
// editable: gen/x.c lines 10-40
  10| ...
```

Not in the project, so their behavior is unknown (external code): name_a, name_b.
Already shown above: name_c.
Not sent this time because of the size limit; ask again if you still need them: name_d.
Answer again with the same JSON format. You can ask 1 more time.
~~~

- 정의 블록은 지금의 `definitions_block`과 같은 형식이다. 고칠 수 있는지(editable / reference only)는 종류의
  `edits_definitions`로 정한다. 참고만인 종류는 줄 번호 없는 지금의 참고용 형식이다.
- 비어 있는 줄(없는 이름, 이미 보낸 이름 등)은 쓰지 않는다.
- 마지막 차례에서는 끝 문장을 "No more definitions can be sent. Answer with "need": []."로 바꾼다.
- 색인을 만들 수 없으면(소스 폴더가 없음 등) 정의 블록 대신 "Definitions cannot be looked up now."를 쓰고, 이름들은
  찾지 못한 것으로 다루지 않는다(외부 코드라고 말하지 않는다).

## 5. 프로젝트 색인

- 작업을 만들 때 프로젝트 전체 정의를 저장하지 않는다(수만 개). 대신 처리하는 쪽(worker)이 작업마다 처음 되물을 때
  작업의 소스 폴더(`jobs.source_root`)를 `scan_project`로 한 번 훑어 메모리에 둔다: 이름 → 정의 목록(호출자 조각
  제외), 파일 이름 → 원문.
- 작업자 스레드 여럿이 같은 작업을 처리하므로 색인은 작업마다 한 번만 만든다(잠금). 메모리에는 최근 작업 2개의 색인만
  둔다.
- 되묻기를 쓰지 않는 묶음에서는 색인을 만들지 않는다.

## 6. 작업에 남기는 것

되묻기로 고칠 수 있게 보낸 파일은 분석 당시 기준을 남기기 위해 작업에 저장한다.

- 정의: 작업에 저장하지 않는다. 저장하면 같은 작업의 다른 묶음 첫 요청에 섞여, 첫 요청과 재사용 키가 처리 순서에
  따라 달라진다. 보낸 정의는 대화 기록에 남는다.
- 파일: 고칠 수 있게 보낸 정의의 파일이 작업 `files`에 없으면, 소스 폴더에서 다시 읽어(`decode_source`) 더한다.
  못 읽으면 그 정의는 참고만으로 보낸다.

## 7. 수정 검증

최종 답의 수정은 지금처럼 보낸 범위 안에서만 받는다. 되묻기로 보낸 정의도 범위에 든다. 같은 글이 여러 곳에 있을 때
고르는 순서: 검사 파일의 보낸 범위 → 첫 요청의 정의·호출자 → 되묻기로 보낸 정의(보낸 순서).

다른 파일을 고친 행은 지금처럼 "다른 파일 수정" 칩이 붙고 자동 선택되지 않는다.

## 8. 저장된 답 재사용

- 재사용 키는 지금처럼 첫 요청으로 만든다(되묻기 메시지는 키에 넣지 않는다).
- 저장 값은 행별 결과와 함께, 되묻기로 고칠 수 있게 보낸 파일의 이름과 sha256 목록을 갖는다:
  `{"results": [...], "files": [{"name": ..., "sha256": ...}]}`. 예전 값(결과 목록만)은 파일 목록이 빈 것으로 읽는다.
- 다시 쓸 때 목록의 파일마다: 작업에 같은 sha256으로 있으면 그대로, 없으면 소스 폴더에서 읽어 sha256이 같으면 작업에
  더한다. 하나라도 없거나 다르면 재사용하지 않고 LLM을 부른다.

## 9. 설정

- `.env`의 `LLM_FOLLOW_UPS`: 되물을 수 있는 횟수. 0~3, 기본 2. 범위 밖이나 숫자가 아니면 설정 오류로 알린다(다른
  `LLM_*` 값과 같은 방식).
- 0이면 세 종류 모두 지금과 같은 지시문·스키마로 보낸다.

## 10. 대화 기록과 점검 도구

- 대화 기록은 지금처럼 주고받은 요청을 모두 남긴다. 결과 줄 앞에 "정의 되묻기 N번"을 한 줄 더한다(N이 0이면 없음).
- `scripts/peek_logs.py`:
  - 묶음마다 첫 사용자 메시지와 최종 답을 짝지어 지금의 셈을 한다(되묻기 메시지는 첫 요청이 아니다).
  - 새 절 "되묻기": 되물은 묶음 수와 횟수별 묶음 수(1번 / 2번 / 그 이상), 요청한 이름 수, 그중 정의를 보낸 것 /
    프로젝트에 없던 것 / 이미 보낸 것 / 상한으로 못 보낸 것, 되묻기 뒤 판단이 바뀐 행 수(첫 답과 최종 답 비교).
  - 화면이 한 화면(40줄)을 넘지 않게, 결론이 난 "직접 수정 행이 받은 것" 절은 뺀다.
  - 화면에는 지금처럼 개수와 정해 둔 글만 찍는다. 이름은 임시 폴더의 자세한 목록에만 쓴다.

## 11. 오류 처리

- 되묻는 도중 LLM 오류는 지금의 한 번 요청과 같게 다룬다(서버 오류는 행 오류, 인증·연결 오류는 작업 중단).
- 색인을 만들다 실패하면(폴더 없음, 읽기 오류) 4절의 "찾을 수 없음" 메시지로 대화를 잇는다. 묶음을 오류로 만들지 않는다.
- 파일을 못 읽어 작업에 더하지 못하면 그 정의는 참고만으로 보낸다.

## 12. 테스트

- 가짜 LLM 클라이언트가 정해 둔 답을 차례로 돌려주게 하고, 보낸 메시지와 최종 결과를 본다.
  - `need`가 빈 첫 답 → 요청 1번, 지금과 같은 결과.
  - `need`에 다른 파일의 함수 → 두 번째 메시지에 그 정의(RTE는 editable), 최종 답의 그 파일 수정이 받아들여짐.
  - 없는 이름 → "Not in the project" 줄. 이미 보낸 이름 → "Already shown above" 줄.
  - 마지막 차례의 `need` → 무시하고 최종 처리. 요청 수가 `1 + LLM_FOLLOW_UPS`를 넘지 않음.
  - 식별자가 아닌 값, 11개 이상의 이름, 상한을 넘는 정의.
  - MISRA는 받은 정의가 참고용이고, 그 파일 수정은 거절됨.
- `LLM_FOLLOW_UPS=0`이면 지금 테스트의 메시지·키가 그대로인지.
- 재사용: 되묻기 파일이 그대로면 재사용하고 작업에 파일이 더해짐, 바뀌었으면 LLM을 부름, 예전 저장 값도 읽힘.
- 색인: 같은 작업을 여러 스레드가 처리해도 한 번만 훑음, 소스 폴더가 없으면 "cannot be looked up".
- peek_logs: 되묻기 셈, 이름·경로가 화면에 없음(`secret` 이름), 40줄·118자 안.

## 13. 검토할 점

- LLM이 이미 보낸 이름을 되묻거나, 매번 `need`를 채워 요청 수만 늘리는 경우. 점검 도구의 "이미 보낸 것"과 횟수별 묶음
  수로 본다.
- 되묻기 뒤 "수정"이 늘어도 맞는 수정인지는 Polyspace를 다시 돌려 확인한다.
