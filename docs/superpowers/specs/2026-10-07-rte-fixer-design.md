# Polyspace RTE 수정 제안 서비스 (llm-fix-server) 설계

- 작성일: 2026-10-07
- 상태: 승인됨 (구현 계획: `docs/superpowers/plans/2026-10-07-rte-fixer.md`)

## 1. 배경과 목표

1단계 `llm-probe`로 회사 LLM의 연결과 기능(구조화된 출력 포함)을 확인했다. 2단계는 Polyspace Code Prover가 찾은 문제를 회사 LLM이 판단하고 수정안을 내는 로컬 서비스다.

LLM은 문제를 **찾지 않는다**. Polyspace 결과 엑셀에 나온 지적 하나하나에 대해 고칠지 판단하고, 고친다면 수정 코드를 낸다. 첫 버전은 엑셀의 RTE(Run-Time Error) 시트만 다룬다.

### 범위

포함:
- RTE 시트 읽기
- 소스 파일 짝짓기
- 행별 LLM 판단·수정
- 결과 화면과 JSON API
- 고른 수정을 담은 패치 내려받기
- SQLite 저장과 결과 재사용
- 테스트

제외(나중에 검토):
- MISRA·CodeMetrics 시트
- 엑셀 `status`·`comment` 칸에 결과 다시 쓰기
- 서비스가 소스 폴더를 직접 고치기
- 수정 전후 엑셀 비교
- 헤더 파일(.h)을 LLM에 함께 보내기
- 여러 사용자와 인증
- 서버 배포

### 성공 기준

1. 엑셀과 소스 파일을 올리면 Red/Orange 행마다 판단(수정 / 수정 불필요)과 이유가 나온다. 수정이면 diff도 나온다.
2. 화면에서 고른 수정을 패치 파일 하나로 받아 `git apply`로 적용할 수 있다.
3. 적용한 뒤 Polyspace를 다시 돌리면 "수정" 행의 check가 Green이 되고, 새 Red/Orange가 생기지 않는다. 이 항목은 회사 PC에서 사람이 확인한다.
4. "수정 불필요" 행의 이유는 검토자가 Polyspace `comment`에 그대로 옮길 수 있는 수준이다.

## 2. 실행 환경과 기술 선택

- 실행 위치: LLM에 접속되는 회사 Windows PC. 서비스는 `127.0.0.1`에서만 열린다.
- 실행 명령: `uv run llm-fix-server` (옵션 `--port`, 기본 8000). `.env`와 같은 프로젝트 루트에서 실행한다.

| 항목 | 선택 | 이유 |
|---|---|---|
| 웹 | FastAPI + uvicorn | 업로드, HTML, JSON을 한 앱에서 처리한다. 시험용 `/docs` 화면이 자동으로 생긴다. |
| 업로드 | python-multipart | 엑셀 업로드와 폼 입력에 필요하다. |
| 엑셀 | openpyxl | `.xlsx` 읽기 |
| 저장 | sqlite3 (표준 라이브러리) | 작업·행·캐시 저장. DB는 `private/fixer.db`이며, 이 폴더는 이미 git에서 제외되어 있다. |
| 백그라운드 처리 | 데몬 스레드 2개와 큐 (`worker.daemon_pool`) | 별도 큐 서버 없이 서비스 안에서 처리한다. `ThreadPoolExecutor`는 끌 때 LLM 응답을 기다려 Ctrl+C가 오래 걸려서 쓰지 않는다. |
| diff·패치 | difflib (표준 라이브러리) | |
| HTML | 문자열 + `html.escape` | 페이지가 둘뿐이라 템플릿 엔진을 쓰지 않는다. |
| LLM | 기존 `load_settings()`·`get_client()`, `json_schema` 출력 | 1단계 점검에서 `json_schema`가 tool calling과 같은 속도로 동작했다. |
| 개발 | httpx (FastAPI `TestClient`에 필요) | |

## 3. 프로젝트 구조

```
src/llm_lab/
├─ polyspace.py   # 엑셀 → RTE 행 목록
├─ sources.py     # 소스 폴더에서 파일 찾기, 디코딩
├─ folder_picker.py # 윈도우 폴더 선택 창 (같은 PC에서만)
├─ fixer.py       # 엔진: 행 하나 → LLM 판단·수정 → 적용 가능한 수정
├─ patch.py       # 고른 수정 → 패치 바이트
├─ store.py       # SQLite: 작업, 파일, 행, 캐시
├─ worker.py      # 뒤에서 행을 하나씩 처리하는 작업자
├─ pages.py       # 결과 화면 HTML
└─ web.py         # FastAPI 경로, CLI 진입점 main()
```

- `pyproject.toml` 스크립트에 `llm-fix-server = "llm_lab.web:main"`을 추가한다.
- 엔진(`polyspace`·`sources`·`fixer`·`patch`)은 FastAPI를 import하지 않는다. 그래서 웹 없이 따로 테스트할 수 있다.

## 4. RTE 시트 읽기 (`polyspace.py`)

**시트 고르기**
- 이름이 `_Result`로 끝나는 시트 중에서, 헤더 행에 필수 열이 모두 있는 시트를 고른다. 이름의 대소문자는 구분하지 않는다.
- 그런 시트가 여러 개면 이름에 `RTE`가 들어간 시트를 쓴다.
- 없으면 오류를 낸다. 오류에는 시트 이름 목록과 각 시트에서 찾은 헤더를 함께 담는다.

**헤더 행 찾기**
- 위에서부터 30행까지 훑어서, 필수 열이 모두 있는 첫 행을 헤더로 본다.
- 셀 값은 앞뒤 공백을 지우고 대소문자를 무시해서 비교한다.

**열**
- 필수: `TYPE`, `File`, `line`, `check`, `detail`
- 선택: `ID`, `Group`, `information`, `Function`, `status`, `comment`. 선택 열이 없으면 빈 문자열로 둔다.

**행 → `Finding`**
- 엑셀 행 번호와 위 열 값을 담는다.
- 헤더 아래에서 모든 칸이 빈 행은 건너뛴다.
- `TYPE` 텍스트로 대상을 고른다. 셀 배경색은 보지 않는다.
  - 공백을 정리하고 대소문자를 무시한 값이 `red check`이면 Red, `orange check`이면 Orange다.
  - `gray check`와 그 밖의 값은 대상에서 빼되, 몇 행을 뺐는지는 센다.
- `line`이 정수가 아니면 그 행은 "줄 번호 없음" 오류 행이 된다.

## 5. 소스 폴더에서 파일 찾기 (`sources.py`)

**디코딩**
- UTF-8로 읽는다. UTF-8 BOM이 있으면 떼고 BOM이 있었다고 기억한다.
- UTF-8로 안 되면 CP949로 읽는다.
- 둘 다 안 되면 그 파일은 "인코딩 미지원"이다.

**줄바꿈**
- 파일에 `\r\n`이 하나라도 있으면 CRLF, 아니면 LF로 기억한다.
- CRLF와 LF가 섞인 파일은 받지 않는다. 패치의 원본 줄 바이트가 어긋나 `git apply`가 거부하기 때문이다. 그 행은 "소스 없음"으로 표시하고 "줄바꿈을 한 가지로 맞춘 뒤 올리세요"라고 안내한다.
- 내부에서는 `\n`으로 통일한 텍스트를 쓴다.
- 파일마다 다음을 남긴다: 인코딩, 줄바꿈, BOM 여부, 원본 바이트의 sha256. 마지막 줄바꿈 유무는 텍스트에서 바로 안다.

**소스 폴더 (2026-10-08 변경)**

처음에는 소스 파일을 하나씩 골라 올렸다. 지금은 사용자가 소스 폴더 경로를 붙여넣으면 서버가 그 폴더에서 파일을 찾는다. 서비스가 같은 PC에서 돌기 때문에 가능하다.

- **입력:** 경로 앞뒤 공백과 따옴표를 뗀다. 탐색기의 "경로로 복사"는 따옴표를 붙인다. 폴더가 없거나 비어 있으면 업로드 직후 `400`으로 알려준다.
- **폴더 찾기 버튼(`folder_picker.py`):** 누르면 서버가 같은 PC에서 윈도우 폴더 선택 창(tkinter `askdirectory`)을 띄우고, 고른 경로를 칸에 채운다.
  - 창은 서버와 분리된 프로세스에서 띄운다. Tk 문제가 서버를 멈추지 않게 하기 위해서다.
  - 결과는 ASCII json으로 받으므로 한글 경로도 그대로 온다.
  - 창은 한 번에 하나만 띄우고, 맨 위에 보이게 하며, 10분이 지나면 포기한다.
  - tkinter가 없는 Python이면 그렇다고 안내하고 붙여넣기로 쓰게 한다.
  - 요청에는 페이지 스크립트가 붙이는 `X-Folder-Picker` 헤더가 있어야 한다. 그래서 다른 사이트가 몰래 창을 띄울 수 없다(CORS 사전 요청을 허락하지 않음).
- **목록 만들기(`list_files`):** 폴더 아래를 훑어 엑셀에 나온 파일 이름과 같은 파일만 상대 경로(`/` 구분)로 모은다. `.git`처럼 점으로 시작하는 폴더는 건너뛴다.
- **고르기(`locate_files`):** 엑셀 경로마다 파일 이름이 같은 후보 중에서 경로 끝부분(폴더 이름들)이 가장 길게 겹치는 것을 고른다. 대소문자는 무시한다. 엑셀 경로가 다른 PC의 절대 경로여도, 상대 경로나 파일 이름뿐이어도 된다.
- **못 고를 때:** 그 행은 "소스 없음"이 되고 이유를 적는다. 이유는 셋 중 하나다.
  - 폴더에 그 이름의 파일이 없다.
  - 같은 이름 파일이 여럿인데 끝부분 일치 길이도 같다. 후보 경로를 함께 보여준다.
  - 디코딩에 실패했다.
- **이름과 저장:** 읽은 파일의 `SourceFile.name`은 폴더 기준 상대 경로다. 이 이름이 프롬프트의 File, 대화 기록, 패치 경로에 그대로 쓰인다. 읽은 내용은 작업과 함께 저장하므로, 나중에 소스가 바뀌어도 결과와 패치는 분석 당시 기준이다.
- **폴더 밖:** 지정한 폴더 밖의 파일은 읽지 않는다. 목록이 폴더 안을 훑어서만 나오기 때문이다.

**나중에: 브라우저에서 폴더 올리기 (B안)**

서비스를 다른 서버에 올려 여러 사람이 쓰게 되면 서버가 사용자 PC의 폴더를 읽을 수 없다. 그때는 다음과 같이 한다.

- 브라우저의 폴더 선택(`<input type="file" webkitdirectory>`)으로 폴더를 통째로 올린다. 브라우저는 파일마다 폴더 기준 상대 경로(`webkitRelativePath`)를 함께 보낸다.
- 그 상대 경로 목록을 `locate_files`에 그대로 넘기면 짝짓기 규칙이 같다. `list_files` 대신 업로드 목록을 쓰는 것만 다르다.
- 폴더에 빌드 결과물이나 `.git`이 있으면 수천 개가 올라간다. 페이지 스크립트로 `.c`/`.h`만 골라 보내거나, 엑셀을 먼저 올려 필요한 파일 이름을 받은 뒤 그 파일만 보내는 2단계 업로드를 검토한다.
- 그때는 `127.0.0.1` 고정 바인딩과 TrustedHost 설정을 바꾸고, 사용자 인증과 작업별 접근 권한을 붙여야 한다. 대화 기록과 DB에 회사 소스가 남으므로 보관 위치도 정해야 한다.

## 6. 엔진 (`fixer.py`)

### 6.1 LLM에 보낼 코드 범위

1. 파일이 `WHOLE_FILE_MAX_LINES`(2,000) 줄 이하면 파일 전체를 보낸다.
2. 더 길면 지적된 줄이 들어 있는 함수를 보낸다.
   - 지적된 줄을 감싸는 최상위 `{ … }` 블록을 찾는다. 이때 주석, 문자열, 문자 상수 안의 중괄호는 무시한다.
   - 시그니처도 넣기 위해 `{` 위쪽 줄을 최대 10줄까지 더한다. 빈 줄, `;`나 `}`로 끝나는 줄, 전처리 줄을 만나면 멈춘다. 그래서 함수 바로 위의 주석도 함께 들어간다.
3. 블록을 못 찾거나, 블록이 `WHOLE_FILE_MAX_LINES` 줄 이상으로 길면 지적된 줄의 앞뒤 60줄을 보낸다.
4. 각 줄 앞에 원래 파일의 줄 번호를 `  57| ` 형식으로 붙인다.

`WHOLE_FILE_MAX_LINES`는 처음에 400이었다. `llm-probe --context`로 컨텍스트 길이를 잰 뒤 2,000으로 올렸다. 2,000줄은 대략 2만~3만 토큰으로 잰 길이에 넉넉히 들어가고, 같은 파일의 매크로·전역 변수·다른 함수까지 LLM이 볼 수 있다.

### 6.2 프롬프트

시스템 메시지에 담을 내용:
- 역할: C 코드 안전성 검토자. Polyspace Code Prover의 런타임 검사 결과 하나를 판단한다.
- 색의 뜻: Red는 오류가 증명된 것, Orange는 안전을 증명하지 못한 것이다.
- 판단 기준
  - Red는 원칙적으로 고친다.
  - Orange는 실제로 문제가 되는 실행 경로가 있으면 고친다. 보낸 코드 안에서 안전이 보장되면 `no_fix`로 답하고, 근거가 되는 줄 번호와 이유를 쓴다.
- 수정 원칙
  - Polyspace가 안전을 증명할 수 있는 형태로 고친다. 예: 명시적 범위 검사, 0 나누기 검사, 초기화.
  - 동작 변경과 수정 범위는 최소로 한다. 지적과 관계없는 줄은 건드리지 않는다.
- 보낸 코드에 없는 정의(매크로, 타입, 다른 함수)는 추측하지 않는다. 판단에 영향을 주면 이유에 그렇게 적는다.
- `reason`은 한국어로 쓴다.

사용자 메시지에 담을 내용:
- 지적 정보: `TYPE`, `check`, `detail`, `Group`, `information`, `Function`, 파일 이름, `line`
- 6.1의 줄 번호가 붙은 코드

프롬프트를 바꿀 때마다 `PROMPT_VERSION` 상수를 올린다. 이 값은 캐시 키에 들어간다(6.6).

### 6.3 응답 형식 (`json_schema`, strict)

```json
{
  "decision": "fix | no_fix",
  "reason": "string",
  "edits": [{ "original": "string", "replacement": "string" }]
}
```

- `original`은 보낸 코드에서 줄 번호 표시를 뺀 연속된 줄들을 그대로 옮긴 것이다.
- `no_fix`면 `edits`는 무시한다.

### 6.4 수정 적용

`fix`의 각 edit를 6.1에서 보낸 범위 안에서 찾는다.

1. **줄 번호 표시 떼기:** LLM이 `    57| ` 같은 줄 번호 표시까지 복사했으면 뗀다. `original`에 그런 줄이 하나라도 있으면 `original`과 `replacement` 모두에서 그 형태로 시작하는 줄마다 뗀다. 새로 쓴 줄에는 번호가 없을 수 있기 때문이다.
2. **끝 줄바꿈 맞추기:** `original`이 줄바꿈으로 끝나는데 `replacement`가 그렇지 않으면 줄바꿈을 붙이고, 반대면 뗀다. 그래야 다음 줄이 붙거나 빈 줄이 생기지 않는다.
3. **그대로 찾기:** `original`이 정확히 한 번 나오면 그 위치가 바뀔 구간이다. 2번 이상 나오면 실패다.
4. **공백 무시 찾기:** 3에서 한 번도 못 찾으면 줄 단위로 비교한다. 각 줄의 연속 공백을 한 칸으로 줄이고 앞뒤 공백을 지운 뒤 비교한다. 연속된 줄들이 정확히 한 번 맞으면 그 줄들 전체(마지막 줄바꿈 제외)가 바뀔 구간이다.
5. **실패 조건:** 다음 중 하나면 실패다.
   - 위 두 방법으로 0번 또는 2번 이상 맞는다.
   - `original`이 비어 있다.
   - 한 응답 안의 edit 구간끼리 겹친다.
   - 적용한 결과가 원본과 같다.

결과는 원본 텍스트 기준의 구간 목록 `(시작, 끝, 바꿀 텍스트)`으로 저장한다. 그래서 행마다 독립적이고, 패치를 만들 때 다시 쓸 수 있다.

화면에 보일 diff는 서버가 원본과 적용 결과를 difflib로 비교해서 만든다(앞뒤 3줄).

### 6.5 LLM 호출

- `client.with_options(timeout=120, max_retries=1)`을 쓴다.
- 출력 한도(`max_tokens`)는 걸지 않는다. 생각(reasoning) 토큰이 출력 한도에 포함되는 모델에서는 한도를 걸면 답이 잘릴 수 있기 때문이다.
- `finish_reason`이 `length`면 "응답 잘림" 실패로 처리한다.
- 다음 경우에는 대화에 이전 응답과 문제 설명을 붙여 **한 번만** 다시 요청한다. 문제 설명의 예: "edits[1].original을 보낸 코드에서 찾을 수 없음".
  - 응답이 JSON이 아니다.
  - 스키마와 맞지 않는다.
  - 6.4 적용에 실패한다.

  두 번째도 실패하면 그 행은 오류다.
- 네트워크, SSL, 인증 오류는 `llm_lab.probe.classify_error`와 `FATAL_CATEGORIES`로 분류한다. 이 오류가 나면 행이 아니라 작업 전체를 멈춘다(7절).

### 6.6 재사용(캐시)

캐시 키는 아래 값을 이어 붙인 문자열의 sha256이다.
- `PROMPT_VERSION`
- 모델명
- 원본 파일 sha256
- 행의 `TYPE`, `check`, `detail`, `Group`, `information`, `Function`, `line`

키가 같으면 LLM을 부르지 않고 저장된 결과를 쓴다. 작업이 달라도 재사용한다.

## 7. 작업 처리와 저장 (`store.py`, `web.py`)

**테이블**

| 테이블 | 내용 |
|---|---|
| `jobs` | id, 생성 시각, 엑셀 파일 이름, 시트 이름, 제외한 행 수, 상태(`running` / `done` / `stopped`), 메시지, 소스 폴더(`source_root`, 스키마 2에서 추가, 예전 작업은 `''`) |
| `files` | job_id, 이름(소스 폴더 기준 상대 경로, 예전 작업은 파일 이름), 텍스트, 인코딩, 줄바꿈, BOM, sha256 |
| `rows` | job_id, 엑셀 행 번호, `Finding` 열 값, 짝지은 파일, 상태(`pending` / `running` / `done` / `error` / `no_source`), 결과 JSON, 오류 메시지 |
| `cache` | 키, 결과 JSON, 생성 시각 |

**처리**
- 작업자는 프로세스 전체에서 하나인 데몬 스레드 2개다. 끄면 처리 중인 행은 버리고, 다음에 켤 때 이어서 처리한다.
- 작업을 만들면 `pending` 행을 하나씩 제출한다.
- 행 하나의 처리 순서는 다음과 같다.
  1. `pending`일 때만 `running`으로 바꾼다(한 번의 UPDATE). 같은 행이 두 번 제출됐으면 먼저 바꾼 작업자만 처리한다.
  2. 캐시를 조회한다.
  3. 캐시에 없으면 엔진을 호출한다.
  4. 결과를 저장한다.
- 남은 `pending`·`running` 행이 없으면 작업은 `done`이다.
- 치명 오류(네트워크·SSL·인증)가 나면 다음과 같이 처리한다.
  - 작업은 `stopped`가 되고, 메시지에 원인 안내를 담는다.
  - 아직 `pending`인 행은 처리하지 않는다.
  - "다시 시도"로 이어서 처리할 수 있다.
- 서비스를 켤 때 다음을 복구한다.
  - `running`으로 남은 행을 `pending`으로 되돌린다.
  - `running` 작업의 `pending` 행을 다시 제출한다.
  - `stopped` 작업은 자동으로 다시 시작하지 않는다. 네트워크·인증 문제가 풀렸는지 알 수 없어 켜자마자 같은 이유로 다시 멈추기 쉽다. "다시 시도" 버튼으로 이어서 처리한다.

**SQLite**
- 호출마다 짧게 연결을 열고 닫는다.
- WAL 모드를 쓴다.
- 표 구조 버전을 `PRAGMA user_version`에 적는다(지금 1). 버전을 적기 전 DB(0)는 구조가 같아 그대로 1로 올린다. 프로그램보다 새 버전 DB면 서비스를 켜지 않고 `git pull`을 안내한다.
- 쓰기는 스레드 잠금 하나로 직렬화한다.

**대화 기록 (`transcript.py`)**
- 행을 처리할 때마다 `private/llm-logs/시각_job작업번호_row엑셀행.md`를 남긴다. 같은 이름이 있으면 `-2`, `-3`을 붙여 덮어쓰지 않는다.
- 내용
  - 맨 위: 행 정보, 모델, 보낸 주소, 함께 보낸 값(`chat_template_kwargs` 등), 결과
  - 요청마다: 보낸 메시지 원문, 받은 내용 원문, `finish_reason`, 토큰 수, 걸린 시간, 응답 원문 JSON
  - 오류가 났으면 오류 메시지
- 캐시를 재사용해 LLM을 부르지 않은 행도 "LLM에 보낸 요청이 없습니다"라는 파일을 남긴다. 그래야 기록이 빠진 건지 헷갈리지 않는다.
- API 키나 헤더는 적지 않는다.
- 파일을 못 써도 행 처리는 계속한다.

## 8. 화면과 API (`web.py`)

| 경로 | 내용 |
|---|---|
| `GET /` | 새 분석: 폼(① 엑셀 1개, ② 소스 폴더 경로(최근에 쓴 폴더를 목록으로 제안), ③ 분석 시작)과 최근 작업 10개 |
| `GET /results` | 작업 목록: 최근 100개, Red/Orange 개수와 상태(처리 중이면 끝난 행/전체 행) |
| `POST /pick-folder` | 헤더 `X-Folder-Picker: 1`이 있어야 한다(없으면 `403`). 윈도우 폴더 선택 창을 띄우고 `{"path": …}`(취소면 `null`) 또는 `{"error": …}`를 돌려준다. |
| `POST /results` | 필드 `excel`, `source_dir`. 폴더를 확인하고 엑셀을 읽어 소스 폴더에서 파일을 찾아 작업을 만든 뒤 `303`으로 `/results/{id}`에 보낸다. 시트·열 오류면 `400` HTML로 원인을 보여준다. |
| `GET /results/{id}` | 결과 페이지 |
| `POST /results/{id}/fixes.patch` | 고른 행 id 목록을 받아 `fixes.patch`를 내려준다. 겹치는 수정이 있으면 `409` HTML로 겹친 행 쌍을 보여준다. |
| `POST /results/{id}/retry` | `error` 행과, 멈춘 작업의 `pending` 행을 다시 처리하고 `/results/{id}`로 보낸다. |
| `GET /api/results/{id}` | 작업과 모든 행의 결과를 JSON으로 준다. |

**화면 공통**
- 맨 위 막대에 서비스 이름과 "새 분석", "작업 목록" 메뉴를 둔다.
- 글자 16px(맑은 고딕), 카드형 배치, 색 대비를 높인 배지를 쓴다.
- 탭 제목은 "화면 이름 · 서비스 이름"이다(예: "작업 3 결과 · rte.xlsx · Polyspace RTE 수정 제안").
- 외부 CSS·스크립트·글꼴을 쓰지 않는다. 작은 스크립트(걸러 보기, 모두 선택, 복사)는 페이지 안에 둔다.

**결과 페이지**
- 맨 위: 작업 번호, 엑셀 이름, 상태 배지, 시트 이름, 시작 시각
- 개수 칸: Red, Orange, 제외(Gray 등), 수정, 수정 불필요, 오류·소스 없음
- 걸러 보기 버튼: 전체 / 수정 / 수정 불필요 / 오류·소스 없음 / 대기 (개수가 0인 분류는 숨김)
- 행마다 카드 하나
  - 왼쪽 띠 색으로 Red/Orange를 구분한다.
  - 머리: TYPE 배지, check, `파일:줄 · 함수()`, 판단(또는 상태) 배지, "적용" 체크박스
  - 본문: 엑셀 행 번호와 detail, LLM 판단 근거(파란 상자), diff(추가·삭제 줄 색 표시), 오류 메시지
- 처리 중일 때
  - 진행 막대와 "끝난 행/전체 행"을 보여주고, `<meta http-equiv="refresh" content="5">`로 새로 고친다.
  - 체크박스는 보이지 않는다. 새로 고칠 때 선택이 사라지기 때문이다.
- 작업이 끝났을 때
  - 새로 고침이 멈춘다.
  - `done`이면서 `fix`인 행에 체크박스가 생긴다.
  - 패치 적용 방법: 기준 폴더(9절)와 명령 두 줄(`git -c core.autocrlf=false apply --check fixes.patch`, `git -c core.autocrlf=false apply fixes.patch`), 명령마다 "복사" 버튼
  - 화면 아래에 따라오는 막대: "적용할 수정 N개 선택됨 (수정 M개 중)", "수정 모두 선택"/"모두 해제" 토글, "패치 내려받기"(하나도 안 고르면 눌리지 않음)
- 멈췄으면 그 메시지를 빨간 상자로 보여준다. 오류 행이나 멈춘 작업이 있으면 "오류 행 다시 시도" 버튼을 보인다.

**서버 켜기**
- `llm-fix-server`는 터미널에 접속 주소를 눈에 띄게 한 줄로 찍고, 포트가 열리면 기본 브라우저로 첫 화면을 연다(최대 15초 기다림).
- `--no-browser`로 끌 수 있다. `--port`로 포트를 바꾼다.

## 9. 패치 (`patch.py`)

**경로**
- 소스 폴더를 지정한 작업은 그 폴더가 "기준 폴더"이고, 패치 안의 경로는 `SourceFile.name`(폴더 기준 상대 경로)이다.
- 아래는 파일을 하나씩 올리던 예전 작업에만 쓰는 규칙이다.
- 작업에서 짝지은 파일들의 엑셀 경로를 `/`로 통일한다. 각 경로의 부모 폴더들에서 공통된 앞부분을 Windows처럼 대소문자를 무시하고 구한다(표기는 첫 경로를 따른다). 이 폴더가 "기준 폴더"다. 파일이 하나뿐이면 그 파일의 부모 폴더가 기준 폴더다.
- 드라이브가 달라 공통 폴더가 없으면 파일 이름만 있을 때처럼 처리한다.
- 패치 안의 경로는 기준 폴더에서 본 상대 경로다(`a/src/x.c`, `b/src/x.c`).
- 엑셀 경로가 파일 이름뿐이면 다음과 같이 한다.
  - 상대 경로는 파일 이름이다.
  - 기준 폴더는 "소스 파일이 있는 폴더"라고 안내한다.

**만들기**
1. 고른 행의 구간을 파일별로 모아 시작 위치 순으로 정렬한다. 두 행이 위치와 내용까지 똑같은 수정을 냈으면 하나만 남긴다. 같은 줄에 Red와 Orange가 함께 있을 때 흔하다.
2. 겹치는 구간이 있으면 겹친 행 쌍 목록으로 실패한다. 맞닿기만 한 구간은 허용한다.
3. 뒤쪽 구간부터 적용해 새 텍스트를 만든다.
4. 파일마다 `difflib.unified_diff`(앞뒤 3줄)로 diff를 만들고 `--- a/…`, `+++ b/…` 헤더를 붙인다. 원본이나 결과에 마지막 줄바꿈이 없으면 `\ No newline at end of file` 표시를 넣는다.
5. 각 파일의 diff를 그 파일의 줄바꿈과 인코딩으로 바이트로 바꾼다. BOM이 있던 파일은 첫 줄에 BOM을 되살린다.
6. 파일별 바이트를 이어 붙인다. 인코딩이 서로 다른 파일이 섞여도 `git apply`는 파일별 바이트로 맞추므로 문제없다.

**적용 명령**

Git for Windows는 기본 설정이 `core.autocrlf=true`다. 이 상태에서 `git apply`를 쓰면 git 저장소 안팎 모두에서 LF 파일이 CRLF로 바뀐다. 실제 `git apply`로 확인한 동작이다.

패치는 이미 파일마다 원래 줄바꿈을 담고 있으므로, 변환을 끈 `git -c core.autocrlf=false apply`로 바이트 그대로 적용하게 안내한다. 이 명령 문자열은 `patch.APPLY_COMMAND` 상수 하나로 두고 화면과 테스트가 같이 쓴다.

## 10. 오류 처리

| 상황 | 처리 |
|---|---|
| RTE 시트나 필수 열 없음 | 업로드 직후 `400`. 시트 이름과 각 시트에서 찾은 헤더를 보여준다. |
| Red/Orange 행이 없음 | 작업은 만들되 바로 `done`. "고칠 행 없음"이라고 표시한다. |
| 줄 번호가 정수가 아님 | 그 행만 `error` |
| 소스 없음, 이름 모호, 인코딩 미지원, 줄바꿈 섞임 | 그 행만 `no_source`. 이유를 적는다. |
| 지적된 줄이 파일 길이를 넘음 | 그 행만 `error`. 엑셀과 소스 버전이 다를 수 있다고 안내한다. |
| 응답 형식 오류, 원문 불일치, 응답 잘림 | 한 번 다시 요청하고, 그래도 실패하면 그 행만 `error` |
| 네트워크·SSL·인증 오류 | 작업 `stopped`. `classify_error`의 안내 문구를 보여준다. |
| 서비스 재시작 | 7절의 복구 절차를 따른다. |
| 겹치는 수정을 함께 고름 | 패치 요청에 `409`. 겹친 행 쌍을 보여준다. |

- `test_web.py`: FastAPI `TestClient`로 확인한다. 테스트에서는 작업자를 바로 실행하는 방식으로 바꿔 끼운다.
  - 업로드 → 결과 페이지 → JSON API → 패치 내려받기
  - `400`·`404`·`409` 응답, 처리 중 화면, 다시 시도

엔진 테스트는 텍스트 처리(`test_fixer_edits.py`)와 LLM 호출(`test_fixer.py`)로 나눈다.

## 12. 완료 확인 절차

회사 PC에서 다음을 확인한다.

1. `uv sync`, `uv run llm-fix-server`로 서비스를 켜고 실제 Polyspace 엑셀과 소스 폴더 경로를 준다.
2. Red/Orange 행이 모두 처리되고, 판단·이유·diff가 읽을 만한지 본다.
3. 몇 개를 골라 패치를 받고, 화면이 안내하는 기준 폴더에서 `git -c core.autocrlf=false apply --check fixes.patch` 후 `--check` 없이 다시 실행한다.
4. Polyspace를 다시 돌려 "수정" 행이 Green이 되었는지, 새 Red/Orange가 없는지 확인한다.
