# Polyspace CodeMetrics 리팩터링 제안 (llm-fix-server의 CodeMetrics 종류) 설계

- 작성일: 2026-10-08
- 상태: 사용자 검토 대기
- 선행 조건: 시트 종류 공용 기반(MISRA 준비 작업에서 만든다)이 master에 올라온 뒤 구현한다. 13절이 그 기반에 바라는 것이다.
- 이 저장소는 공개다. 이 문서와 테스트에는 회사 엑셀의 실제 값(시트 이름, 행 수, 기준치, 파일·함수 이름)을 넣지 않고 일반적인 예만 쓴다.
- 조건(기준치, 단계 수, 지표 목록, 열 배치)은 회사 양식이라 바뀔 수 있다. 코드·프롬프트·테스트에 상수로 박지 않고 작업마다 엑셀에서 읽는다(사용자, 2026-10-08).

## 1. 배경과 목표

`llm-fix-server`는 Polyspace 결과 엑셀의 RTE 시트를 읽어, 행마다 회사 LLM이 판단·수정을 내고, 고른 수정을 패치 하나로 준다(`2026-10-07-rte-fixer-design.md`). 같은 엑셀에는 CodeMetrics 결과 시트도 있다. 이 시트의 행은 오류 지적이 아니라 **함수의 측정값이 한도를 넘었다**는 기록이다(예: 복잡도 한도 10, 실제 값 14).

CodeMetrics도 RTE처럼 다룬다. 엑셀 → 대상 행마다 판단(수정 / 수정 불필요)과 이유 → 수정이면 diff → 고른 수정을 패치로 → Polyspace를 다시 돌려 확인. 다른 점은 "수정"이 버그 수정이 아니라 **동작을 바꾸지 않는 리팩터링**이라는 것이다.

### 사용자와 정한 것 (2026-10-08)

| 항목 | 결정 |
|---|---|
| 진행 방식 | RTE와 같은 흐름 |
| 수정 범위 | 같은 파일 안에서만. `static` 도우미 함수를 더할 수 있다. 함수 이름·인자·반환형과 다른 파일·헤더는 그대로 둔다. |
| 동작 확인 | 사람이 diff를 검토한다. 단위 테스트는 없다고 본다. |
| 접근 | A안: 함수 단위로 LLM을 한 번 부르고, LLM은 함수 범위를 통째로 대신할 코드를 낸다. 서버가 바뀐 줄만 남겨 diff·패치를 만든다. |
| 단계 | 조건 시트의 단계(Pass / 가운데 / Fail) 중 가운데와 Fail 행을 모두 처리한다. 화면에 단계를 보여 주고, "수정 모두 선택"은 Fail만 고른다. |

버린 안:
- B안(함수 단위 + RTE식 "원문 → 바꿀 글"): 수십 줄 블록을 옮길 때 원문을 정확히 베끼지 못해 "위치를 못 찾음" 실패가 잦을 것으로 봤다.
- C안(행 단위): 한 함수에 지표가 여럿 걸리면 수정끼리 겹친다. 또 한 지표를 고치다 다른 지표를 나쁘게 만든다.

### 성공 기준

1. 대상 함수마다 행별 판단과 이유가 나온다. 수정이면 diff가 나온다.
2. 고른 수정을 패치 하나로 받아 `git apply`로 적용할 수 있다.
3. 적용한 뒤 Polyspace를 다시 돌리면 다음을 만족한다. 이 항목은 회사 PC에서 사람이 확인한다.
   - "수정" 행이 CodeMetrics 결과에서 사라진다(한도 안으로 들어온다).
   - 새로 만든 도우미 함수를 포함해 새 지표 위반이 생기지 않는다.
   - RTE·MISRA 위반도 새로 생기지 않는다.
4. "수정 불필요" 이유는 검토자가 Polyspace `comment`에 그대로 옮길 수 있는 수준이다.

## 2. Polyspace 지표 정의 (MathWorks 문서)

프롬프트와 판단 규칙이 이 정의를 따른다. 아래 표는 Polyspace 지표에 대한 공개된 지식이고, 회사가 어떤 지표를 검사하는지 정한 목록이 아니다. 검사하는 지표와 한도는 작업마다 엑셀에서 읽는다. 표에 있는 지표가 작업에 나오면 그 요령을 붙이고, 없는 지표는 공통 지시만 준다.

| 지표 (Check) | 세는 법 | 같은 파일 안에서 줄이는 법 |
|---|---|---|
| Cyclomatic Complexity | 결정 지점 + 1. `if`, `else if`, `for`, `while`, `?:`는 하나씩 센다. `case`는 뒤에 `break`가 있을 때만 센다. `&&`·`||`는 세지 않는다. 매크로를 펼친 뒤에 센다. | 응집된 분기나 `case` 본문을 도우미로 뺀다. `else`가 없는 겹친 `if`는 `&&`로 합친다. |
| Number of Called Functions | 본문에서 부르는 **서로 다른** 함수 수. 표준 라이브러리 함수도 센다. 함수 포인터 호출과 `assert`는 세지 않는다. | 함께 쓰이는 호출들을 의미 있는 도우미로 묶는다. |
| Number of Call Levels | 이름과 달리 호출 깊이가 아니다. `if`·`switch`·`for`·`while`이 **겹친 깊이**다. `else if`는 한 단계 더 겹친 `if`로 센다. R2023b부터 0에서, 그 전에는 1에서 센다. | 안쪽 블록을 도우미로 뺀다. 같은 값을 비교하는 긴 `else if` 사슬을 `switch`로 바꾼다. |
| Number of Calling Functions | 이 함수를 부르는 **서로 다른** 함수 수 | 부르는 쪽 파일을 바꿔야 한다. 정한 범위 밖이라 늘 "수정 불필요"다. |

Polyspace 옵션 `-consider-switch-as-single-decision`을 쓰면 `switch` 전체가 결정 지점 하나다. 회사 설정에서 이 옵션을 쓰는지는 14절에서 확인한다.

## 3. 시트 읽기와 대상 행

**시트와 열**
- 시트는 공용 기반의 규칙을 따라 고른다(종류 선택, `_Result`로 끝나는 시트, 필수 열 확인).
- 열 이름은 앞뒤 공백을 지우고 대소문자를 무시해 비교한다.
  - 필수: `File`, `Function`, `line`, `Check`, `Threshold`, `Actual Value`
  - 선택: `Status`, `Comment`
- `Threshold`·`Actual Value`는 원문 글자로 저장한다. 숫자 해석은 CodeMetrics 쪽에서 한다.

**대상 고르기** (위에서부터 처음 맞는 것)

| 조건 | 결과 |
|---|---|
| `Function`이 비어 있음 | 제외 "파일 단위 지표" |
| `Threshold`나 `Actual Value`가 숫자가 아님 | 제외 "비교할 수 없음" |
| `Actual Value` ≤ 그 행의 `Threshold` | 제외 "한도 안" |
| `Actual Value` > 그 행의 `Threshold` | 대상 |

- 숫자는 정수·소수, 그리고 쉼표 자릿수 표기(`1,234`)를 받는다.
- 제외한 행 수는 이유별로 작업에 남긴다.
- 모든 지표를 "클수록 나쁨"으로 본다. "이 값 이상이어야 하는" 지표(예: Comment Density)는 지금 다루지 않는다(14절).
- `line`이 정수가 아니면 그 묶음은 RTE처럼 "줄 번호 오류"다.

## 4. 묶음과 한도

**묶음**
- 키: (`File`을 `/`로 통일하고 대소문자를 무시한 값, `Function`에서 끝의 `()`와 공백을 뗀 이름)
- 묶음 하나에 LLM 호출 하나다. 같은 묶음의 행들은 같은 함수 범위를 쓴다. 범위는 묶음 첫 행의 `line`으로 찾는다.

**지표별 처리**

| 지표 | 처리 |
|---|---|
| Cyclomatic Complexity, Number of Called Functions, Number of Call Levels | LLM이 판단한다. |
| Number of Calling Functions | 서버가 "수정 불필요"로 정한다. LLM은 이유만 쓴다. |
| 그 밖의 지표 | LLM이 공통 지시로 판단한다. |

지표 이름은 공백을 한 칸으로 줄이고 대소문자를 무시해 비교한다.

**조건 시트와 단계**
- 엑셀에는 결과 시트와 따로 CodeMetrics 조건 시트가 있다. 지표마다 단계가 여러 행으로 적혀 있다. 예: `1 ~ 10` Pass / `11 ~ 20` 가운데 / `>= 21` Fail(수정 필요).
- 조건 시트 읽기는 조건 통합 작업이 만든다(13절). CodeMetrics는 지표마다 (단계 목록, Pass 상한)만 받는다. 단계 하나는 (하한, 상한, 판정 글, 종류)이고, 종류는 pass / middle / fail이다.
- **지표 이름 잇기:** 결과 시트의 `Check`와 조건 시트의 지표 이름은 다를 수 있다. 예: "Max. Number of Calling Functions"와 "Number of Calling Functions".
  - 이름을 낱말로 나눈다. 문장 부호를 빼고, 소문자로 바꾸고, 복수 `s`를 떼고, `number`·`of`·`max`·`maximum`·`the` 같은 낱말을 뺀 뒤 낱말 집합이 같은 지표끼리 잇는다.
  - 짝이 없거나 여럿이면 잇지 않는다. 작업 머리에 "조건 시트에서 짝을 찾지 못한 지표 N개"를 보여 준다.
- **행의 단계:** 실제 값이 든 단계다. 조건 시트가 없거나, 지표를 잇지 못했거나, 어느 단계에도 들지 않으면 "단계 모름"이다.
- 단계는 대상 고르기를 바꾸지 않는다. 3절의 "한도 초과"면 가운데든 Fail이든 처리한다. 단계는 화면 표시와 기본 선택(9절)에만 쓴다.

**한도 표**
- (지표 → 한도 숫자)를 두 곳에서 모은다.
  - 조건 시트의 모든 지표(Pass 상한). 지금 결과 시트에 위반이 없는 지표까지 들어간다.
  - 결과 시트의 모든 행(`Threshold`). 대상인지와 상관없다.
- 같은 지표에 값이 여럿이면 가장 작은 값을 쓴다. 두 곳의 값이 다르면 작업 머리에 알린다.
- 프롬프트에 "모든 함수가 지켜야 할 한도"로 넣는다. 도우미 함수를 늘리다 다른 지표 한도를 넘지 않게 하려는 것이다.
- 한도 표는 함수 하나(`metric_limits`)에서만 만든다. 작업마다 엑셀에서 새로 만들고, 상수로 두지 않는다.

## 5. 함수 범위와 보낼 코드

**함수 찾기** (`function_range(text, line, name)`)
1. 최상위 `{ … }` 블록을 찾는다. 기존 `_top_level_blocks`를 그대로 쓰므로 주석·문자열·문자 상수 속 중괄호는 무시한다.
2. `line`을 품는 블록을 고른다. 없으면 `line` ≤ 시작 줄 ≤ `line` + 10인 첫 블록을 고른다. 정의 줄과 `{`가 다른 줄인 경우다.
3. 시그니처 시작 줄은 `{` 줄에서 위로 거슬러 올라가 정한다(최대 10줄). 빈 줄, `;`·`}`로 끝나는 줄, 전처리 줄, 주석만 있는 줄을 만나면 멈춘다. 반환형이 이름 윗줄에 따로 있는 시그니처(`static void` / `foo(void)`)도 이렇게 하면 통째로 들어온다. 정한 시작 줄이 `line`보다 아래면 "함수를 찾지 못함"이다.
4. 시그니처 바로 위의 "주석만 있는 줄"을 빈 줄이 나올 때까지 거슬러 올라가 범위에 넣는다. 줄 수 제한은 없다.
   - 주석만 있는 줄인지는 `_top_level_blocks`처럼 주석·문자열 상태를 따라가며 정한다.
   - 그래서 `*`로 시작하지 않는 블록 주석의 가운데 줄도 주석으로 알아본다.
   - 범위가 주석이나 시그니처 한가운데서 시작하면 도우미 함수가 그 사이에 끼어 코드가 깨진다. 그래서 이 판정을 글자 모양(`//`, `*`로 시작하는지)이 아니라 상태로 한다.
5. 시그니처 시작 줄부터 `{` 줄까지에 함수 이름이 식별자로 있고, 바로 뒤에 `(`가 와야 한다. 없으면 "함수를 찾지 못함"이다.
6. 범위가 `FUNCTION_MAX_LINES`(1,000줄)보다 길면 LLM을 부르지 않고 "너무 긺"이다. 함수를 통째로 다시 써야 해서 응답이 잘리기 때문이다.

**바꿀 범위**는 4의 주석(없으면 시그니처) 첫 줄부터 닫는 `}` 줄까지다. 도우미 함수는 이 범위 맨 위에 들어간다. 그래서 원래 주석이 함수와 떨어지지 않고, 도우미를 쓰기 전에 정의가 있어 프로토타입이 필요 없다.

**보낼 코드**
- 파일이 `WHOLE_FILE_MAX_LINES`(2,000줄) 이하면 파일 전체를 보낸다. 넘으면 바꿀 범위만 보낸다.
- 각 줄 앞에 원래 줄 번호를 붙이는 RTE 방식(`  57| `)을 쓴다.
- 사용자 메시지에 "N~M줄을 대신할 코드로 답하라"를 적는다.

## 6. 프롬프트

시스템 메시지는 영어로 쓰고(RTE와 같음) 아래를 담는다. CodeMetrics용 `PROMPT_VERSION`은 RTE와 따로 둔다.

- **역할:** C 함수 하나를 Polyspace 코드 지표 한도 안으로 리팩터링한다. 동작은 바꾸지 않는다.
- **범위 규칙**
  - 지정한 줄 범위만 대신할 코드를 낸다.
  - 함수 이름, 인자, 반환형, 지정자(`static` 등)를 그대로 둔다.
  - 새 전역 변수를 만들지 않는다. 다른 함수, 다른 파일, 헤더를 건드리지 않는다.
  - `static` 도우미 함수를 범위 맨 위에 더할 수 있다.
    - 이름은 31자 이내이고 파일 안에서 겹치지 않아야 한다.
    - 함수마다 한 줄 주석을 단다.
- **동작 보존**
  - 문장을 기계적으로 옮긴다. 계산·호출·전역 접근의 순서와 부작용을 그대로 둔다.
  - 원래 주석을 지우지 않는다.
  - 필요한 값은 인자로 넘기고, 바뀌는 값은 포인터로 돌려받는다.
  - 중간 `return`, `goto`, 재귀, 동적 메모리는 새로 쓰지 않는다. 새 코드도 MISRA C:2012를 따른다(예: 15.5 한 출구, 8.8 `static`).
- **지표별 요령:** 2절 표의 마지막 열을 그대로 준다.
- **한도:** 4절의 한도 표를 주고, 도우미를 포함한 모든 함수가 모든 한도 안에 있어야 한다고 적는다.
- **판단:** 행마다 고른다.
  - `fix`: 낸 코드로 그 지표가 한도 안에 들어온다.
  - `no_fix`: 규칙 안에서 줄일 수 없거나, 동작이 바뀔 위험이 크다.
  - Number of Calling Functions 행은 언제나 `no_fix`다.
- **이유:** 한국어 1~3문장으로, Polyspace `comment`에 그대로 붙일 수 있게 쓴다.
  - `fix`면 무엇을 어디로 옮겼고 값이 대략 얼마가 되는지 쓴다(예: "상태별 처리 세 덩어리를 static 함수로 나눠 복잡도를 약 8로 낮춤").
  - `no_fix`면 그 까닭을 쓴다.
- 보낸 코드에 없는 정의(매크로, 타입, 다른 함수)는 추측하지 않는다. 판단에 영향을 주면 이유에 그렇게 쓴다.
- JSON으로만 답한다. `fix` 행이 없으면 `code`는 `""`다.

사용자 메시지에 담는 것:
- 함수 이름, 파일 이름(소스 폴더 기준 상대 경로), 바꿀 줄 범위
- 묶음의 행 표: 엑셀 행 번호, 지표, 실제 값, 한도
- 한도 표
- 5절의 줄 번호를 붙인 코드

## 7. 응답 형식과 검사

**형식** (`json_schema`, strict)

```json
{
  "rows": [{ "row": 0, "decision": "fix | no_fix", "reason": "string" }],
  "code": "string"
}
```

`row`는 엑셀 행 번호다. `code`는 바꿀 범위 전체를 대신할 글이다.

**검사 순서**
1. `finish_reason`이 `length`면 "응답 잘림"이다.
2. JSON과 스키마를 확인한다.
3. `rows`의 행 번호가 묶음의 행 번호 집합과 정확히 같아야 한다. 빠짐, 중복, 모르는 행은 실패다.
4. Number of Calling Functions 행이 `fix`면 실패다("이 행은 no_fix여야 함").
5. `fix` 행이 하나라도 있으면 `code`를 확인한다.
   - 비어 있지 않다.
   - 소스 인코딩(CP949 등)으로 쓸 수 있다.
   - 주석·문자열을 뺀 중괄호 짝이 맞다.
   - **시그니처를 지킨다.** 원본의 시그니처 시작 줄부터 `{` 앞까지에서 주석을 빼고 공백을 한 칸으로 줄인 글이, 같은 방식으로 줄인 `code` 안에 그대로 있어야 한다. 함수 이름·인자·반환형을 바꾸면 여기서 걸린다.
   - 범위를 `code`로 바꾼 결과가 원본과 다르다.
6. `fix` 행이 없으면 `code`는 보지 않는다.

3~5에서 실패하면 RTE처럼 대화에 이전 응답과 문제 설명을 붙여 **한 번만** 다시 요청한다. 문제 설명의 예는 "rows에 엑셀 12행이 없음", "함수 시그니처가 바뀜"이다. 두 번째도 실패하면 묶음의 모든 행이 오류("확인 필요")가 된다. 화면 설명은 기존 `user_error` 형식으로 쓰고, 첫 줄 문구를 더한다:
- "LLM이 함수 이름이나 인자를 바꿨습니다."
- "LLM 답에 빠진 행이 있습니다."

## 8. 수정 만들기

1. 바꿀 범위의 원본 위치 `(start, end)`를 정한다. 마지막 줄의 줄바꿈은 범위에 넣는다.
2. `code`의 줄바꿈을 `\n`으로 통일하고, 끝에 줄바꿈이 없으면 붙인다.
3. `Edit(start, end, code)` 하나를 기존 `_minimize`에 넣어 실제로 바뀐 줄 단위의 수정 목록으로 줄인다.
4. diff는 `display_diff(이름, 원본, 적용 결과)`로 만든다.
5. 결과를 행에 나눈다. 공용 기반의 묶음 방식을 따른다.
   - `fix` 행은 자기 이유와 묶음 공통의 수정 목록·diff를 갖는다.
   - `no_fix` 행은 이유만 갖는다.

패치는 기존 `patch.py`를 그대로 쓴다. 같은 함수의 `fix` 행을 여럿 골라도 수정 목록이 똑같으므로 하나로 합쳐진다. 서로 다른 함수의 범위는 겹치지 않으므로 CodeMetrics 작업 안에서는 겹침 충돌이 생기지 않는다.

## 9. 화면, 저장, 캐시, 시간

공용 기반이 정한 틀에 맞춰 CodeMetrics 몫만 정한다.

- **새 분석:** 첫 화면에서 종류 "CodeMetrics"를 고른다. 공용 기반의 "작업 하나에 시트 하나" 방식이다.
- **결과 카드:** 머리에 다음을 보여 준다.
  - 지표 이름
  - 단계 배지: Fail(빨강) / 가운데(주황) / 단계 모름(회색). 배지 글은 조건 시트의 판정 글을 쓴다.
  - `실제 값 > 한도` 배지
  - `파일:줄 · 함수()`
  - 판단 배지
  
  같은 묶음의 diff는 묶음의 첫 `fix` 행에만 보여 준다. 다른 `fix` 행에는 "같은 함수의 수정 (엑셀 N행과 같음)"이라고 적는다.
- **개수 칸:** Red/Orange 대신 단계별(Fail / 가운데 / 단계 모름)과 지표별 대상 행 수를 둔다. 그 밖은 수정 / 수정 불필요 / 확인 필요 / 제외(이유별)로, RTE와 같다.
- **기본 선택:** "수정 모두 선택"은 Fail이나 단계 모름인 `fix` 행만 고른다. 가운데 단계 행은 사람이 검토해서 골라 넣는다.
  - 수정 목록은 묶음이 함께 쓴다. 그래서 Fail 행 하나를 고르면 그 함수의 리팩터링 전체가 패치에 들어간다. 같은 함수의 가운데 단계 행도 함께 고쳐진다.
  - 아래 막대에 "가운데 단계 수정 N개는 직접 고르세요"를 보여 준다.
- **패치 선택:** 겹침 자동 선택의 우선순위는 단계(Fail 먼저), 그다음 엑셀 행 순서다.
- **캐시 키:** 다음 값을 이어 붙인 글의 sha256이다.
  - CodeMetrics `PROMPT_VERSION`, 모델명, 파일 sha256, 바꿀 범위(시작·끝 줄)
  - 묶음 행들의 (지표, 실제 값, 한도)를 행 번호 순으로 이은 것
  - 한도 표
- **시간:** LLM 대기는 `CODEMETRICS_TIMEOUT`(300초)이다. 함수를 통째로 쓰므로 RTE의 120초보다 길다. 출력 한도(`max_tokens`)는 걸지 않는다(RTE와 같은 이유).
- **대화 기록:** RTE처럼 `private/llm-logs/`에 남긴다. 맨 위에는 묶음의 행 목록을 적는다. 회사 PC 안에서만 본다.

## 10. 오류 처리

| 상황 | 처리 |
|---|---|
| 필수 열 없음 | 공용 기반의 업로드 오류(`400`)와 같다. |
| 대상 행이 없음 | 작업을 만들되 바로 `done`. 제외 이유별 개수를 보여 준다. |
| 소스 없음·이름 모호·인코딩·줄바꿈 섞임 | 묶음의 모든 행이 `no_source`(RTE와 같다). |
| `line`이 정수가 아니거나 파일보다 김 | 묶음의 모든 행이 오류. 엑셀과 소스 버전이 다를 수 있다고 안내한다. |
| 함수를 찾지 못함 | 묶음의 모든 행이 오류. 함수 이름과 줄 번호가 소스와 맞는지 보라고 안내한다. |
| 함수가 너무 긺 | 묶음의 모든 행이 오류. LLM을 부르지 않는다. "직접 나누거나 사유를 적으세요"라고 안내한다. |
| 응답 잘림·형식 오류·행 빠짐·시그니처 바뀜 | 한 번 다시 요청한다. 그래도 실패하면 묶음의 모든 행이 오류다. |
| 네트워크·SSL·인증 오류 | 작업 `stopped`(RTE와 같다). |

## 11. 테스트

모두 회사 LLM 없이 돌아간다. 예시 코드와 엑셀은 일반적인 이름(`a.c`, `foo`)으로 만든다. 한도·단계 값은 회사 값을 옮기지 않고, 테스트마다 다른 여러 값을 쓴다. 지표 개수와 단계 개수도 바꿔 가며 확인한다.

- **대상 고르기:** 한도 초과, 한도 안, 같음, 비교 불가, 쉼표 숫자, 빈 Function, 제외 이유별 개수
- **묶기와 한도 표**
  - `()` 떼기, 경로 표기 차이
  - 같은 지표의 한도가 여럿일 때 가장 작은 값
  - 조건 시트에만 있는 지표의 한도 포함, 두 곳 값이 다를 때 알림
- **단계와 이름 잇기**
  - 단계 2개·3개·4개
  - 이름이 다른 지표 잇기, 짝 없음, 짝 여럿
  - 어느 단계에도 들지 않는 값, 조건 시트 없음 → 단계 모름
  - 기본 선택이 Fail·단계 모름만 고름
- **함수 찾기**
  - `{`가 정의 줄에 있는 경우와 다음 줄에 있는 경우
  - 여러 줄 시그니처, 위 주석 포함·빈 줄로 떨어진 주석 제외
  - 주석·문자열 속 중괄호
  - 이름 불일치로 못 찾음, 너무 긺
- **응답 검사**
  - 정상 `fix`, 모두 `no_fix`(이때 `code` 무시)
  - 행 빠짐·중복·모르는 행, Calling Functions를 `fix`로 답함
  - 시그니처 바뀜, 중괄호 짝 틀림, 인코딩 불가, 원본과 같음, 응답 잘림
  - 다시 요청한 뒤 성공과 실패
- **수정 만들기**
  - 범위 교체 뒤 `_minimize`로 바뀐 줄만 남는다.
  - 도우미 추가와 블록 이동의 diff
  - 화면이 안내하는 `APPLY_COMMAND`로 실제 적용한 결과가 바이트 단위로 같다(CRLF·CP949 포함, git이 없으면 건너뜀).
- **통합:** 공용 기반이 올라온 뒤 가짜 LLM으로 업로드 → 결과 화면 → JSON API → 패치까지 한 번 돌린다.

## 12. 회사 PC 확인 절차

`todo.md`에 절로 넣는다. 사용자에게는 회사 정보 없이 개수와 종류만 받는다(전역 규칙).

1. `git pull` 뒤 `uv run llm-fix-server`를 켠다. 종류 "CodeMetrics"를 고르고, 같은 엑셀과 소스 폴더로 분석한다.
2. 수정 / 수정 불필요 / 확인 필요 / 제외 개수와, "확인 필요" 설명 첫 줄의 종류를 받는다.
3. diff를 검토한다. 동작이 바뀐 것 같은 수정이 몇 개였고 어떤 식이었는지 말로 받는다.
4. 패치를 적용하고(`--check` 먼저) Polyspace를 다시 돌린다.
5. 새 엑셀로 `uv run python scripts/peek_metrics.py "새 엑셀 경로.xlsx"`를 돌려 지표별 행 수를 분석 전과 비교한다. 이 화면은 회사 정보를 찍지 않으므로 그대로 캡처해도 된다. RTE·MISRA 위반이 새로 생겼는지는 개수만 받는다.

## 13. 공용 기반에 바라는 것

이름과 모양은 기반을 따른다. CodeMetrics가 기반에서 꼭 필요로 하는 동작은 다음과 같다.

- 종류별 필수·선택 열과 원문 필드 자리(`Threshold`, `Actual Value`). 옛 `rows.finding` JSON도 읽혀야 한다.
- 종류별 대상 고르기 함수. 제외 행 수와 이유를 함께 돌려준다.
- 종류별 묶음 기준.
  - 묶음 하나에 LLM 호출 하나다.
  - 판단과 이유는 행마다 둔다.
  - 수정 목록은 묶음이 함께 쓰고 `fix` 행에만 복사한다.
- 종류별 엔진 호출(코드 범위, 프롬프트, 응답 처리), 캐시 키, LLM 대기 시간
- 종류별 카드 머리, 개수 칸, 겹침 우선순위, "수정 모두 선택"이 고를 행

조건 통합 작업(조건 시트 읽기)에 바라는 것:
- 작업마다 엑셀에서 CodeMetrics 조건 시트를 읽어 지표마다 (지표 이름, 단계 목록, Pass 상한)을 준다.
  - 단계 하나는 (하한, 상한, 판정 글, 종류)다.
  - 종류는 판정 글로 정한다. "Pass"가 들어 있으면 pass, "Fail"이 들어 있으면 fail, 그 밖은 middle이다.
- 헤더 행은 훑어서 찾고, 열은 헤더 글로 찾는다. 병합 셀이 남긴 빈 열과, 이름이 첫 단계 행에만 있는 모양을 견딘다.
- 범위 글은 느슨하게 읽는다(`1 ~ 10`, `>= 21`, `>=21`처럼 공백이 다른 표기).
- 조건 시트가 없거나 읽지 못하면 빈 결과와 이유를 준다. 이때 CodeMetrics는 결과 시트의 `Threshold`만으로 동작한다.

## 14. 확인을 기다리는 것과 나중 일

| 항목 | 영향 | 확인 방법 |
|---|---|---|
| 조건 시트의 나머지 지표 이름·단계와 가운데 단계의 판정 글 | 이름 잇기, 단계 배지 | 조건 통합 작업의 2차 확인 결과 |
| 이름 잇기 규칙(낱말 집합 비교)이 실제 이름에 맞는지 | 단계와 한도 표 | 첫 실행의 "짝을 찾지 못한 지표 N개"를 보고 빼는 낱말을 고친다. |
| 조건 시트에 지표의 방향(이하/이상)이나 적용 여부가 있는지 | 대상 고르기 | 조건 통합 작업의 2차 확인 결과 |
| `-consider-switch-as-single-decision` 사용 여부 | 복잡도 요령 문구(`case` 세는 법) | Polyspace 설정을 사용자에게 묻는다. |
| Polyspace 버전(Call Levels를 0과 1 중 어디서 세는지) | 없음. 시트의 실제 값과 한도가 같은 방식으로 나온다. | 필요 없음 |
| `FUNCTION_MAX_LINES` = 1,000 | 긴 함수를 LLM에 보낼지 | 첫 실행 뒤 조정 |
| 2,000줄이 넘는 파일에서는 함수만 보냄 | 매크로·타입 정의가 안 보인다. | 프롬프트가 "추측하지 말고 이유에 쓰라"고 지시한다. 결과를 보고 파일 머리를 함께 보낼지 정한다. |

나중 일(이번에 만들지 않음):
- "이상이어야 하는" 지표(Comment Density 등)
- 파일 단위 지표
- 서버가 지표 값을 직접 어림해 LLM 답을 미리 걸러 내는 것. 예: 도우미 함수의 복잡도 계산.
- 시그니처 변경이 필요한 지표(인자 수 등)를 여러 파일에 걸쳐 고치는 것
